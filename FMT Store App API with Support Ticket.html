FMT Store App API

01 · Orientation

Getting started

The API is stateless. Three pieces of context travel in headers instead of a session: who the user is, which branch they are shopping, and which cart belongs to them.

Call GET /bootstrap once at launch. It returns app config, both WhatsApp numbers, the branch list and a default_store_id to preselect.

# 1. Launch
curl https://www.fmtonlinestore.com/api/v1/bootstrap

# 2. Browse a branch's catalog
curl -H "X-Store-Id: 26" \
     https://www.fmtonlinestore.com/api/v1/products?per_page=12

# 3. Add to cart as a guest — response returns a cart_token to keep
curl -X POST -H "X-Store-Id: 26" -H "Content-Type: application/json" \
     -d '{"product_id":2275,"quantity":2}' \
     https://www.fmtonlinestore.com/api/v1/cart/items

Typical first-run flow

  • Bootstrap → store the branch list, preselect default_store_id, cache both WhatsApp numbers.
  • Browse → catalog endpoints work for guests. Stock always reflects the branch in X-Store-Id.
  • Cart → guests get a cart_token on first add. Persist it in secure storage.
  • Login / register → send the stored X-Cart-Token with the call and the guest cart is merged into the account automatically.
  • Checkout → requires a Bearer token. Guest checkout is not allowed, same as the website.

02 · Request context

The three headers

HeaderWhenNotes
Authorization Logged-in calls Bearer <token> from register or login. Required for checkout, orders and account.
X-Store-Id Catalog & cart Selected branch id. Drives all stock and inventory checks. Omitted → falls back to the first active branch.
X-Cart-Token Guest cart UUID returned by any cart response. Not needed once the user is logged in, but harmless to keep sending.

Send both when logging in

If the user built a cart as a guest, include X-Cart-Token on the register/login call. The server merges those lines into the account cart and deletes the guest cart. Quantities are summed when the same item exists in both.

Every /api/ response is JSON, whether or not you send Accept: application/json.

03 · Contract

Response and error shapes

Success

{
  "success": true,
  "message": "Product added to cart.",   // may be null
  "data": { /* endpoint payload */ }
}

Validation error — 422

Laravel's standard shape. Map errors straight onto form fields.

{
  "message": "The email field must be a valid email address. (and 1 more error)",
  "errors": {
    "email":   ["The email field must be a valid email address."],
    "message": ["The message field is required."]
  }
}

Business rule rejected — 422

Stock and cart failures. message is written for display.

{
  "success": false,
  "message": "Only 7 unit(s) available in stock.",
  "errors": { "cart": ["Only 7 unit(s) available in stock."] }
}

Status codes

CodeMeaning
200OK
201Created — register, place order, contact
401{"message":"Unauthenticated."} — token missing, expired or revoked. Send the user to login.
404Product, store, blog or order not found
422Validation or business rule
429Throttled — login 10/min, password reset and contact 5/min

04 · Endpoints

Auth

POST/auth/registerPublic

Creates the account, saves the first address and returns a token. Mirrors the website's signup fields exactly.

Required: name, email, whatsapp, alternate_number, city, district, password (min 6, with password_confirmation). Optional device_name labels the token.

{
  "success": true,
  "message": "Registered successfully.",
  "data": {
    "token": "12|bHE0RlrFYNT4xZuRtBTG...",
    "user": {
      "id": 523,
      "name": "Ayesha Khan",
      "email": "ayesha@example.com",
      "contact": "03001234567",
      "alternate_number": "03011234567"
    }
  }
}
POST/auth/loginPublic

Two modes. Default is email. Send login_type: "whatsapp" with a whatsapp field to log in by number instead — the same choice the website offers.

// by email
{ "email": "ayesha@example.com", "password": "••••••" }

// by WhatsApp number
{ "login_type": "whatsapp", "whatsapp": "03001234567", "password": "••••••" }

Wrong credentials return 422 keyed on email or whatsapp — not 401.

GET/auth/meAuth

Current user. Use it on resume to confirm the stored token is still valid.

POST/auth/logoutAuth

Revokes only the token used for this call, so other devices stay signed in.

POST/auth/forgot-passwordPublic

Emails a reset link to email. An unknown address returns 422.

POST/auth/reset-passwordPublic

Completes the reset with token, email, password, password_confirmation. Capture the token from the emailed link via deep link, or let the user open the web page.

DELETE/auth/accountAuth

Permanent deletion, confirmed with the current password. Required by the Apple App Store because the app offers registration.

What deletion actually removes

The account, its saved address and its cart are deleted, and every token is revoked, so the user is signed out everywhere immediately. Past orders are kept as financial records — they simply stop being linked to a customer, and each order keeps its own billing name, phone and address. Word the confirmation screen accordingly rather than promising that order history disappears.

How a variable product is priced in a listing

A variable product keeps its prices on its variants, so the card's regular_price and sale_price are taken from its cheapest active variant, and price_from / price_to give the spread for a "Rs 900 – Rs 1,500" label. stock_status is true when any one variant has stock at the branch. See Variable products.

GET/products/{slug}Public

Full detail with gallery, variants and related products.

Variant stock

Each variant carries stock_qty and in_stock, and every attribute value carries in_stock — true when at least one variant holding that value has stock. Use it to disable sold-out options instead of letting the add-to-cart call fail. For a variable product, the product's stock_qty is the sum across variants.

    "product": {
      "id": 4635,

      "regular_price": "1000.00", // cheapest variant
      "sale_price": "900.00",
      "price_from": 900,
      "price_to": 1500,
      "bulk_price": 800,       // product-level; variants override
      "min_bulk_qty": 5,

      "variants": [
        { "id": 10, "sku": "TG-S", "regular_price": "1000.00",
          "sale_price": "900.00", "bulk_price": 800, "min_bulk_qty": 5,

            "attribute_name": "Size", "value_id": 3, "value": "Small" }] },

Variable products

A product is "type": "variable" when it sells in variants — size, colour, capacity. Everything that matters commercially (price, stock, SKU, bulk threshold) lives on the variant; the product row is a container for them.

1 · In listings

Price the card from price_from / price_to when they differ, and treat stock_status as "something is available" rather than a specific variant.

{ "id": 4637, "type": "variable",
  "regular_price": "1200.00",  // cheapest variant's regular
  "sale_price": "900.00",      // cheapest variant's sale
  "price_from": 900, "price_to": 1500,
  "discount": 25,
  "stock_status": true }         // at least one variant has stock

2 · Render the picker

Build one option group per entry in attributes. Each value carries in_stock, true when at least one variant holding that value has stock at the selected branch. Disable the others instead of letting the add-to-cart call fail.

3 · Resolve the selection to a variant

Match the chosen value_ids against variants[].attribute_values[].value_id. The variant whose value set equals the selection is the one being sold: show its price, and cap the quantity stepper at its stock_qty.

4 · Add it to the cart

POST /cart/items
{ "product_id": 4637, "variant_id": 12, "quantity": 10,
  "variant_label": "Small" }

// the resulting cart line
{ "cart_key": "4637_v12", "variant_id": 12,
  "variant_label": "Small", "quantity": 10,
  "unit_price": 900, "bulk_price": 850,
  "min_bulk_qty": 10, "effective_price": 850 }

variant_label is the text you show the customer — join the selected values, e.g. "Small / Red". The server keeps it on the cart line and copies it onto the order, so the invoice and the WhatsApp confirmation message both read correctly. Send it; nothing reconstructs it for you.

One line per variant

A variant's cart_key is {product_id}_v{variant_id} — 4637_v12 above. The same product appears once per chosen variant, so always address lines by cart_key for PATCH and DELETE, never by product_id.

5 · Pricing and stock follow the variant

  • Bulk pricing uses the variant's bulk_price and min_bulk_qty, falling back to the product's only where the variant leaves them unset. In the example above the price drops from Rs 900 to Rs 850 at quantity 10.
  • Stock is checked against that variant's inventory at X-Store-Id. Asking for more returns 422 naming the figure available.
  • Adding a sold-out variant returns 422 "This product is out of stock."

No variable products are live yet

This whole flow is implemented and tested, but every one of the 2,434 products in the catalogue today returns "type": "simple" with empty variants and attributes. Build the picker against this contract; it starts returning data as soon as variable products are published and active. Use /products?type=variable to check.

Cart

Works for guests and logged-in users. Carts are stored server-side, so they survive app reinstalls for logged-in users and persist by token for guests. Every cart response returns the full cart, so you never need a follow-up fetch.

GET/cartPublic

Current cart. With no X-Cart-Token and no Bearer token, a new empty cart and token are issued.

POST/cart/itemsPublic

Body: product_id, quantity, optional variant_id and variant_label. Adding an item already present increases its quantity.

PATCH/cart/items/{cart_key}Public

Sets an absolute quantity. Use the cart_key from the cart response, not the product id.

DELETE/cart/items/{cart_key}Public

Removes one line.

DELETE/cartPublic

Empties the cart.

POST/cart/mergeAuth

Merges the guest cart named by cart_token into the account. Login and register already do this; this is the manual escape hatch.

{
  "data": {
    "cart_token": "06d74083-50f4-4e3b-93a7-69f41e86163d",
    "store_id": 26,
    "items": [{
      "cart_key": "4635_v10",     // "{product}" or "{product}_v{variant}"
      "id": 4635,
      "variant_id": 10,
      "variant_label": "Small",
      "title": "Tempered Glass Pack",
      "image_url": "https://…/thumb.jpg",
      "quantity": 5,
      "unit_price": 900,
      "bulk_price": 800,
      "min_bulk_qty": 5,
      "effective_price": 800  // what the customer pays
    }],
    "totals": { "items_count": 1, "quantity": 5,
                "subtotal": 4000, "total": 4000 }
  }
}

Bulk pricing

Once a line's quantity reaches min_bulk_qty, effective_price switches from unit_price to bulk_price. In the example above, quantity 4 costs Rs 900 each; quantity 5 costs Rs 800 each. Always display effective_price and the server-provided totals rather than recomputing.

To watch it happen against live data, add product 4794 at branch 26: quantity 1 is Rs 900 each, quantity 10 drops to Rs 850 each for a Rs 8,500 subtotal.

Stock is enforced server-side

Adds and quantity increases are capped at the branch's inventory and rejected with 422. Treat the returned message as display copy.

Checkout

GET/checkout/summaryAuth

Recalculated cart, saved address for prefill, branch list, payment methods and the three notice lines shown on the website checkout. Returns 422 when the cart is empty.

POST/ordersAuth

Places the order: revalidates stock, creates the order, emails the customer and the store, then empties the cart.

Required body: billing_name, billing_email, billing_phone, billing_address, billing_city, billing_province, billing_country, payment_method. Optional: billing_zip, order_notes, store_id.

Payment follows the website

Cash on delivery, with a partial advance confirmed over WhatsApp. There is no payment gateway. After a successful order the customer must message the store to confirm — so the response hands you a ready-made deep link.

{
  "success": true,
  "message": "Order placed successfully.",
  "data": {
    "order": {
      "id": 475,
      "status": "pending",
      "payment_method": "COD",
      "total": 1800,

}

Open whatsapp_url directly. The message is prefilled with the order number, branch, every line item, the total, and the customer's own name, phone and address — the customer only presses send. Show a clear "Contact on WhatsApp to confirm" step after checkout, as the website does.

Orders

GET/ordersAuth

The customer's orders across every branch, newest first. Paginated with per_page (default 10, max 50).

GET/orders/{id}Auth

One order plus a fresh whatsapp_url, so the confirmation step can be retried later.

GET/orders/{id}/invoiceAuth

Returns invoice_url — a signed, shareable link to the printable invoice. Open it in a browser or web view; it needs no auth header.

Every order line carries its product thumbnail and slug, so an order screen needs no extra catalog lookups:

{
  "items": [{
    "id": 91,
    "product_id": 4637,
    "variant_id": 12,              // null for a simple product
    "variant_label": "Small",       // null for a simple product
    "product_title": "Tempered Glass Pack",
    "product_slug": "tempered-glass-pack",
    "thumbnail": "https://www.fmtonlinestore.com/storage/…/thumb.jpg",
    "price": 850,                 // charged per unit at the time of sale

Chat

One thread per customer, login only. The conversation is keyed to the account, so there is no thread list to build and no guest chat. Call GET /chat and you have the whole screen.

GET/chatAuth

Conversation plus the newest page of history (30 messages, oldest-first within the page). Pass before_id to page further back. The first call — without before_id — also marks the store's messages as read, exactly as the website does.

Send as multipart/form-data. At least one of body, attachments[] or voice_note is required; an empty send returns 422. Returns 201 with the created message in the shape above.

FieldRules

POST/chat/readAuth

Marks the store's messages read and clears the badge. Call it when the chat screen becomes visible.

Just { conversation_id, unread_count }. Cheap — safe to call on app resume for the tab badge.

Realtime — pick either, or both

Both transports are supported. Polling is simpler and always correct; Pusher is instant. Using polling on the chat screen and push notifications for the background case is a perfectly good shipping position.

GET/chat/messages?after_id=Auth

Everything newer than after_id, oldest first, max 50. Send the newest id you hold (0 on a cold start) and store the returned last_id for the next call. Idempotent — polling the same id twice returns nothing the second time.

GET /chat/messages?after_id=104

{ "data": { "messages": [ /* … */ ],
           "last_id": 105,        // pass this as the next after_id
           "unread_count": 1 } }

Use the app's own auth endpoint

Point your Pusher client at /api/broadcasting/auth and send the bearer token on it. The website's /broadcasting/auth accepts session cookies only and will reject the app. The endpoint receives Pusher's socket_id and channel_name and returns {"auth": "…"}; subscribing to another customer's conversation, or to the staff channel, returns 403.

The message.sent payload is the same message object as above. messages.read carries { conversation_id, user_id, read_by_admin, read_at } — use it to flip your sent ticks. Neither event is delivered to the client that caused it, so keep showing your own sent message optimistically.

Push notifications

Firebase Cloud Messaging, project fmt-app-5611f. Take google-services.json and GoogleService-Info.plist from that Firebase project — the server needs nothing from you but the device token.

POST/devicesAuth

Register the FCM token. Body: token, platform (android | ios | web), optional app_version.

DELETE/devicesAuth

Body: token. Call it on logout so a shared handset stops receiving the previous customer's notifications.

When to call these

Register after every login and again whenever Firebase hands you a rotated token. The token is the unique key, so re-registering updates in place rather than creating duplicates, and a token that moves to a different account is reassigned. Tokens FCM reports as dead are deleted server-side automatically, so you never need to clean up.

GET/notifications/settingsAuth

Returns notify_orders, notify_chat, push_enabled (whether the server is configured to send at all) and devices (how many are registered).

PUT/notifications/settingsAuth

Send either or both toggles: {"notify_chat": false} is valid on its own. These mute our sending only — the OS-level permission is separate, so check both before telling a customer notifications are on.

What arrives, and how to route it

Every push carries a data block. Switch on type to decide which screen to open. All values are strings, as FCM requires.

// the store replied in chat
{ "type": "chat", "conversation_id": "494", "message_id": "105" }

// an order changed status
{ "type": "order", "order_id": "480", "status": "dispatched" }
TriggerTitle / bodyMuted by
Store replies in chat“FMT Online Store” / the message text, or “Sent you a voice note” / “Sent you an attachment”notify_chat
Order status changes“Order #480 dispatched” / “Your order of Rs 1,750 has been dispatched.”notify_orders

Order statuses are pending, confirmed, dispatched, completed and declined. The customer gets the same news by email, so treat the push as a nudge rather than the only delivery. Nothing is pushed for an order placed at the counter or by a guest, because those have no account to notify.

Support tickets

Login only. A ticket belongs to an account — that is what makes tracking possible — so gate the entry point behind login rather than showing a form that will fail. Each ticket carries a human reference like TKT-000123, which is what every endpoint below addresses it by.

This is separate from POST /contact. Contact is a one-way enquiry with no tracking; a ticket is a tracked conversation with a status. Offer both, or only tickets — but don't send problem reports to /contact, because nothing can be followed up there.

Staff keep private notes you never see

Dashboard users can attach internal notes to a ticket. Those are filtered out of replies entirely and never raise the unread count, so the thread you render is exactly what the customer is meant to read. The ticket's internal priority is not exposed either.

POST/support/tickets/{reference}/repliesAuth

Body: body (required, max 5,000). Returns 201 with the updated ticket and thread.

Replying reopens a finished ticket

If the customer replies to a ticket that is resolved, rejected or closed, it goes back to open automatically — so re-read status from the response instead of assuming it is unchanged. Say so in the UI ("replying will reopen this request") so it isn't a surprise.

POST/support/tickets/{reference}/readAuth

Clears one ticket's unread badge without fetching the thread.

GET/support/unreadAuth

Returns { unread_count, open_tickets } across every ticket — cheap enough to call on app resume for a tab badge.

Statuses

ValueMeans
openWaiting on the store
in_progressBeing worked on
resolvedFixed
rejectedNot actionable
closedFinished

Always render status_label rather than formatting status yourself. A ticket only reaches these states when staff move it — the customer cannot set a status.

What the customer is told

  • On submit — a confirmation email carrying the reference.
  • On a staff reply or status change — an email, plus a push with { "type": "ticket", "reference": "TKT-000123", "ticket_id": "123" }. Route on type and open the ticket by its reference.
  • Muted by the notify_support toggle, which sits alongside notify_orders and notify_chat in notification settings.

05 · Before you build

Things that will bite otherwise

  • Stock is per branch. The same product can be in stock at one branch and sold out at another. Always send X-Store-Id, and refresh the product screen after the user switches branch.
  • Switching branch empties the cart. Warn the user before you change X-Store-Id while the cart has items.
  • Never compute totals on the device. Bulk price thresholds apply per line. Use effective_price and totals from the response.
  • Prices are decimal strings in catalog payloads ("5250.00") and numbers in cart payloads. Normalise on parse.
  • Use cart_key, not product_id, for update and delete — a variable product has one line per variant.
  • Checkout needs a login. There is no guest checkout, matching the website. Prompt for login when the cart is not empty rather than at app start.
  • Persist the cart_token in secure storage, and send it on login so a guest cart is not lost.
  • The order is not finished at checkout. It is pending until the customer messages the store on WhatsApp and pays the advance. Make that step prominent.
  • Chat is login-only. There is one thread per account and no guest chat, so gate the chat entry point behind login rather than showing it and failing.
  • Support tickets are login-only too, and are addressed by reference rather than a numeric id. A customer replying to a finished ticket reopens it, so re-read the status from the response.
  • Don't trust a push to arrive. Delivery is best-effort and the customer may have muted it or denied the OS permission. Refresh chat and orders when the app resumes instead of relying on notifications to drive state.
  • Version flags are placeholders. min_version and latest_version currently return 1.0.0 until they are configured server-side. Build the force-update check now; the values will become real.

Not available yet

  • iOS push — Android is ready. iOS additionally needs an APNs key uploaded into the Firebase project; until that is done iOS devices register fine and simply never receive anything, with no error to detect. Confirm it is in place before testing on iPhone.
  • Live variable products — the flow is built and tested (see Variable products), but nothing in the catalogue is variable yet, so you cannot exercise the picker against live data until some are published and active.
  • Ticket attachments — tickets are text only, so there is no way to send a screenshot with one. Point customers at chat, which does take attachments and voice notes.
  • Blog posts — /blogs returns an empty list until posts are published.
